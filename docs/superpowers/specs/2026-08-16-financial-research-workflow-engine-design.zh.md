# Financial Research Multi-Agent Workflow Engine Design

[English](2026-08-16-financial-research-workflow-engine-design.md) | 中文

## Overview

本文定义了一个基于 DeepSeek Harness 的金融分析平台第一子项目：一个面向小型投研团队、以工作流为中心的多智能体研究引擎。

目标部署形态是本地或内网环境。

第一阶段使用公开数据，支持将公司研究、行业背景和轻量量化检查组合在一起的混合研究任务。

这个引擎是执行内核，不是完整产品。

它必须让团队提交研究任务，把任务拆成并行的专责分析步骤，观察执行进度，查看中间证据，并获得带有会话留痕的报告草稿和结构化产物。

## Goals

- 在不依赖人工编排的前提下，跑通一条从任务入口到报告草稿的标准混合研究流程。
- 在同一个 MVP 中平衡三个成功信号：执行稳定、结果可用、过程可观测。
- 保持设计可扩展，让后续研究工作台和金融技能中心可以复用同一个执行内核。
- 优先复用 DeepSeek Harness 已有的能力缝：`workflow`、`subagent`、`tools`、`session` 和对外 API。

## Architecture

这份设计把 `packages/workflow` 作为编排所有者。

Workflow 负责任务模板、节点依赖、节点生命周期、重试、取消和最终汇总。

`packages/subagent` 提供专责分析步骤的执行单元。

Subagent 不负责全局流程控制。

它们接收有界任务上下文，执行聚焦的分析步骤，并返回结构化输出或结构化失败结果。

工具层负责公开数据抓取、标准化、计算、导出和规则检查。

工具层不能把业务流程偷偷塞进一个工具调用里。

`packages/session` 保存模型可见上下文、工作流进度、子智能体回传、中间产物和最终结果的持久化轨迹。

这条基于日志的轨迹，是后续工作台审计与回放的来源。

第一阶段的用户界面可以保持轻量。

聊天入口或 API 入口负责发起研究任务，一个轻量工作台视图读取任务状态、日志和产物即可。

## Core Model

这个引擎定义四个核心对象。

`Research Job` 表示用户请求，以及模板选择、输出目标、优先级和入口元数据。

`Workflow Run` 表示某个模板在该任务上的一次具体执行，包含节点图、状态、依赖、时间线和结束原因。

`Node Run` 表示工作流中的一次单步骤执行。

一个节点可以直接通过工具调用执行，也可以通过委派给子智能体来间接执行。

`Artifact` 表示任何被持久化的中间或最终产物，例如资料包、估值摘要、风险清单或报告草稿。

## Node Types

第一阶段保持精简的节点类型集合。

`Intake` 节点负责校验输入、解析模板、初始化会话留痕，并构建共享任务上下文。

`Tool` 节点负责拉取公开资料、标准化文档、计算指标，并准备可复用的结构化证据。

`Delegation` 节点把有界的专责任务交给子智能体，例如财报解析、新闻归因、估值分析和风险审阅。

`Aggregation` 节点合并结构化结果，识别证据缺口，并构建下游使用的统一证据包。

`Output` 节点生成最终结论、报告草稿和任务级完成结果。

这份设计明确把大型自定义 DSL、跨工作流嵌套、复杂人工审批节点和长周期调度排除在第一阶段之外。

## Execution Flow

一条标准混合研究流程按下面的路径执行。

用户提交一个主题，例如某家公司在行业周期中的投资价值。

引擎创建 `Research Job`，写入初始会话上下文，并把所选模板展开为一个具体的 `Workflow Run`。

工具节点抓取公开数据、财报材料和近期新闻，再把这些输入标准化为可复用证据。

路由逻辑创建并行的委派节点，交给专责智能体处理。

第一阶段至少应支持财报解析、新闻归因、估值分析和风险审阅。

每个专责智能体都要返回结构化结果，说明它的结论、使用了哪些证据，以及还缺什么。

汇总节点把这些结果合并成统一证据包。

产出节点再把证据包转成报告草稿、简洁结论集合和适合工作台展示的任务摘要。

执行结束后，把产物和最终状态写入基于 session 的持久化存储。

## State, Recovery, and Observability

`Workflow Run` 在 `Created`、`Planning`、`Running` 之间流转，并以 `Completed`、`Failed` 或 `Cancelled` 之一结束。

`Node Run` 在 `Pending`、`Ready`、`Running` 之间流转，并以 `Succeeded`、`Failed` 或 `Skipped` 之一结束。

第一阶段支持有限次数的工具失败自动重试。

只要底层 provider 能做到，委派失败就必须返回结构化错误，而不是不透明文本。

非关键节点允许降级继续，但最终报告必须显式标出缺失证据和失败步骤。

第一阶段不要求任意断点恢复、跨天恢复或自动重写工作流图。

最小可观测面应该展示任务树、每个节点的阶段日志、专责智能体归属、重试与失败原因，以及一个能单独查看证据包、风险清单和报告草稿的产物面板。

Harness 的 workflow 事件、subagent report 和 session log 共同提供这层视图。

## First-Phase Scope

第一阶段必须交付一条完整混合研究模板、三到四个专责子智能体、本文定义的五类节点、一组能支撑完整流程的公开数据工具，以及一个最小任务状态查看界面。

第一阶段不包含企业级 RBAC、审批流、私有数据接入、宽泛模板管理、长周期调度，也不追求成熟完整的最终产品壳层。

这一阶段的目标是证明执行内核，而不是完成整个金融平台。

## Verification

单元测试应覆盖节点生命周期流转、依赖解析、重试上限、降级行为和产物汇总。

集成测试应覆盖一条完整混合研究路径，包括任务初始化、工具执行、并行专责分析、结果汇总和输出生成。

失败路径的集成测试应至少覆盖一次可重试工具失败、一次终止型专责失败和一次非关键降级路径。

由于输出同时对产品和模型可见，第一版实现应增加或更新无密钥快照，覆盖任务树摘要、重要执行状态消息和最终研究结果输出。

还应提供一个可运行示例，演示与测试锚定的同一条端到端流程。

第一阶段的验收标准很直接：流程能够稳定完成，团队能够看见发生了什么，结果能够回链到支持证据，并且新增一个专责智能体或工具时不需要重写核心编排器。

## Follow-On Work

执行内核稳定后，下一批子项目是更完整的研究工作台、金融技能中心、更多研究模板和私有数据接入。

这些后续能力应该建立在这个引擎之上，而不是替换它。
